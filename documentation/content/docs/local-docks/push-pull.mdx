---
title: Push and pull
description: Move a dock's disk between a laptop and a control plane with the import and export routes.
---

A dock's disk can move between contexts: a local dock goes up to a control
plane (push), and a fleet dock comes down to a laptop (pull). The `dock push`
and `dock pull` commands in the CLI drive the routes below; the routes are
public, so any client can use them.

Only the disk moves, never memory, so a pushed or pulled dock boots fresh. Both directions need a [microVM](/concepts/docks) host:
a gVisor dock keeps only `/home/user/work`, so it cannot be exported and an
import needs a microVM host to land on. On a real fleet
(`RUNTIME_DRIVER=restate`) an import is refused with `runtime_unsupported` up
front when no online host can take it; the other drivers (the default `fake`
driver used for development) skip that check. The disk must come from a
[Dockyard](/dockyard) image; a dock built from a base made on the host cannot
be exported.

## Push: import a disk

The file you upload is `rootfs.ext4.zst`: the dock's raw ext4 disk, compressed
with zstd. Send its size and sha256 up front.

### Start an import

`POST /v1/docks/import` with a JSON body:

| Field | Description |
| --- | --- |
| `workspaceId` | Workspace the dock is created in |
| `name` | Optional dock name, unique per workspace |
| `image` | The Dockyard image the disk was built from, a name from `GET /v1/images` |
| `cpus`, `memoryMiB`, `diskGiB` | The size of the new dock, as for `POST /v1/docks` |
| `sizeBytes` | Size of the compressed file; at most `diskGiB` GiB |
| `sha256` | Lowercase hex sha256 of the compressed file |

It answers 201:

```json
{
  "importId": "0d6f...",
  "upload": {
    "mode": "direct",
    "partSize": 16777216,
    "parts": [{ "number": 1, "url": "https://store.example.com/..." }]
  }
}
```

Cut the file into `partSize` bytes (the last part may be shorter) and send
each part to its `url` with a `PUT` and the raw bytes as the body. Part numbers
start at 1.

- `direct`: the URL is a presigned object-store URL, valid for 24 hours. Keep
  the `ETag` response header of every part.
- `proxy`: used when the control plane has no store address clients can reach.
  The URL is a path on the control plane (see the next route); send the same
  credentials as for any API call. At most 128 MiB per part.

An organization can hold five open imports at once (`import_limit_reached`,
HTTP 429). Start refuses, before any upload, a `name` already used in the
workspace (`dock_name_taken`, 409), and a member when the organization's
default Environment passes admins-only secrets (`environment_secrets_admin_only`,
403).

### Upload a part through the control plane

`PUT /v1/docks/import/:importId/parts/:number` takes the raw part bytes as the
body (not JSON) and answers `{ "number": 1, "etag": "..." }`. Only the member
who started the import can use it. A part larger than `partSize` is refused
with `part_too_large`. The control plane buffers each part in memory, so it
caps the combined `partSize` of parts in flight (256 MiB per control plane, half
of that per organization). A part past the cap waits its turn for up to 60
seconds, then gets `part_upload_busy` (HTTP 429); send the part again. `dock push`
retries it on its own.

### Complete an import

`POST /v1/docks/import/:importId/complete` with the part numbers and etags:

```json
{ "parts": [{ "number": 1, "etag": "9b2cf5..." }] }
```

List every part exactly once. The control plane joins the parts, checks the
size, records the file as a whole-image snapshot and creates the dock from it
on a microVM host. It answers 202 with the new dock in the `provisioning`
state; the host verifies the sha256 and size when it materializes the disk,
and the dock ends in `error` if the file does not match. Imports land only on
hosts whose docklet registers the `verified-imports` feature, so older docklets
never boot an unverified disk. Repeating the call for a completed
import returns the same dock. If no host can take the dock right now, or the
name was taken meanwhile, the call fails with `no_host_capacity`,
`capacity_exhausted` or `dock_name_taken` and can be repeated without uploading
again. Any other failure ends the import and removes its uploaded parts; start
a new one. The dock boots in the background, so a host that refuses the image
or its base later leaves the dock in `error`, with no error code on this call.

An import that is not completed within 24 hours is removed together with its
uploaded parts.

## Pull: export a disk

### Start an export

`POST /v1/docks/:id/export` answers 202 with `{ "exportId": "..." }`. The host
takes a full, disk-only snapshot of the running dock (the dock keeps running).
The source dock is then re-applied, so its gateway tokens and its dock API key
(`DOCK_API_KEY`) rotate and the copy cannot use them; if they cannot be
rotated, the export fails with `export_failed` rather than publish a disk with
live credentials. Exporting needs the same role as opening the dock: a dock with
connectors, or with secrets from an admins-only environment, can be exported
only by its creator or an admin. Exports are disabled while retention (zero data
retention) is enabled.

A dock must be `ready`, `idle` or `running`. An organization can hold five live
exports at once (`export_limit_reached`, HTTP 429), and a dock one in progress.

### Read an export

`GET /v1/docks/exports/:exportId` answers:

```json
{
  "state": "ready",
  "image": "ubuntu-24.04",
  "cpus": 2,
  "memoryMiB": 4096,
  "diskGiB": 20,
  "sizeBytes": 812646400,
  "sha256": "9f86d0...",
  "baseImage": "ubuntu-24.04",
  "url": "https://store.example.com/...",
  "expiresAt": "2026-10-12T08:00:00.000Z",
  "urlExpiresAt": "2026-10-11T08:15:00.000Z"
}
```

`state` is `pending`, `ready` or `failed`. While pending, `sizeBytes`, `sha256`,
`baseImage` and `url` are `null`. A failed export carries `error`:
`export_base_unsupported` (the dock's disk was not built from a Dockyard image),
`export_failed` or `export_interrupted`.

`url` is a fresh presigned download for `rootfs.ext4.zst` on every call, valid
until `urlExpiresAt` (15 minutes by default; self-hosters set
`SNAPSHOT_STORE_PRESIGN_TTL_SECONDS`); it supports `Range` requests, so a download
resumes. Check the downloaded file against `sha256`. `baseImage` names the
Dockyard image whose kernel boots the disk. The export itself, and its object,
are removed at `expiresAt`, 24 hours after the export starts.

### Download through the control plane

When the control plane has no store address clients can reach, `url` is a path
on the control plane: `GET /v1/docks/exports/:exportId/download` streams the
file, with the same permissions, and honors one `Range` header, `bytes=start-` or
`bytes=start-end`, to resume. A malformed header is ignored and the whole file
is sent. A range that starts at or past the end of the file, or ends before it
starts, answers `416` with `Content-Range: bytes */<size>`, so a client resuming
past the end can restart.

## Errors

| Code | When |
| --- | --- |
| `import_too_large` | 413: the file is bigger than the `diskGiB` disk, either the declared `sizeBytes` at start or the uploaded object at complete. In `proxy` mode also a disk whose part size would pass 128 MiB |
| `import_checksum_mismatch` | 400, from complete: the uploaded size is not the declared one and is not above the disk size (that case is `import_too_large`). A sha256 mismatch found by the host while booting returns no code: the dock goes to `error` |
| `part_too_large` | A proxy part is bigger than `partSize` |
| `part_upload_busy` | 429: the part waited 60 seconds for the organization's or the control plane's share of in-flight proxy parts. Retryable: send the same part again |
| `payload_too_large` | 413: a request body is over the route's size limit (any route, not only imports) |
| `runtime_unsupported` | 409: no online microVM host has a docklet that verifies imported disks (checked only with `RUNTIME_DRIVER=restate`), or the dock to export is not a microVM dock |
| `import_egress_unsupported` | 409, at start (only with `RUNTIME_DRIVER=restate`): the default Environment has an egress allowlist and no host that verifies imports confines egress on resume; upgrade the docklets |
| `host_egress_unsupported` | 503, from complete: no suitable host can apply the default Environment's egress allowlist. Retryable: the uploaded disk is kept |
| `range_not_satisfiable` | 416, from the download: the `Range` starts at or past the end of the file, or ends before it starts; `Content-Range: bytes */<size>` carries the size |
| `dock_name_taken` | 409: the import's `name` is already used in the workspace, at start or at complete. Retryable at complete |
| `dock_not_running` | 409: the dock to export is not `ready`, `idle` or `running` |
| `conflict` | 409: a part is sent to an import that is closed, expired or direct; complete on an import that failed, expired or is already being completed; an export already in progress for the dock; a download of an export that is not `ready` |
| `environment_secrets_admin_only` | 403: a member starts or completes an import while the default Environment passes admins-only secrets, or exports or downloads a dock that holds an admins-only environment's secrets (only its creator or an admin may) |
| `connector_admin_only` | 403: a member exports or downloads a dock with connectors that someone else created |
| `no_host_capacity`, `capacity_exhausted` | Complete found no host to place the dock on; retryable without uploading again |
| `export_base_unsupported` | The exported dock's base is not a Dockyard image (reported as the export's `error`) |
| `import_not_found`, `export_not_found` | Unknown, expired, or not yours to read |
| `import_limit_reached`, `export_limit_reached` | Too many open imports or live exports |
| `zdr_blocks_exports` | 403: exports are disabled while the organization's zero data retention is on |

Every error uses the usual `{ "ok": false, "code", "message" }` envelope.
