Dock is open source (AGPL-3.0) and self-hosting is free. The whole
control plane runs on one machine with Docker Compose from `deploy/self-host/`
in the Dock source; its `README.md` is the full guide. This page summarizes it.
Before exposing an instance, read the [threat model](/threat-model).

| Service | Role |
|---|---|
| `db` (Postgres 16), `redis` | durable state, rate limits |
| `restate` | durable Dock workflows (internal only) |
| `minio` + `minio-init` | Snapshot storage, bucket created on start with default encryption (SSE-S3) |
| `migrate` | applies database migrations, then exits |
| `backend` | REST API, fleet API, GitHub webhooks, workflow endpoint |
| `restate-register` | registers the workflow endpoint with Restate on every start |
| `dashboard` | web UI |
| `caddy` | one public origin: `/v1/*`, `/api/auth/*`, `/openapi.json` to the API, the rest to the dashboard |

## Requirements

- Docker with Compose v2.
- For a public instance, a DNS name pointing at the machine (for example
  `dock.example.com`) and ports 80 and 443 free, so Caddy can obtain a public
  certificate. Plain HTTP works for trying Dock, but GitHub webhooks and
  confined GitHub runs need HTTPS on 443.
- To run Docks on the same machine: Linux with Docker (`gvisor`) or `/dev/kvm` (`microvm`).

## Quick start

From `deploy/self-host/`:

```bash
./setup.sh --host                           # local: http://localhost:8088, Docks on this machine
./setup.sh --url https://dock.example.com   # public instance, automatic HTTPS
```

`setup.sh` writes `.env` with fresh secrets on the first run, pulls the images, starts the stack,
and waits until the API is healthy. `--host` enrolls the same machine as a
host (it asks for sudo, and the first run builds the Dock image; it expects a
`usedock/docklet` checkout next to this repository at `../docklet`: clone
https://github.com/usedock/docklet there, or set `DOCKLET_DIR`).
Re-running keeps `.env`. To configure by hand, copy `.env.example` to `.env`,
fill it, and run `docker compose up -d`.

The stack runs prebuilt images (`ghcr.io/usedock/dock-api`, `dock-api-migrate`,
and `dock-dashboard`, for linux/amd64 and linux/arm64) at the release in
`DOCK_VERSION`, pinned in `.env.example`. To build from source instead, run
`./setup.sh --build`.

Open `DOCK_PUBLIC_URL` and sign up. On a self-hosted instance:

- There is no billing on a self-hosted instance.
- Telemetry is off by default.
- Mail is optional. With `SMTP_HOST` empty, messages such as sign-in codes
  and reset links are written to the API log
  (`docker compose logs backend | grep -A2 "mail not delivered"`).
- Google and GitHub sign-in are optional. A provider appears only when both
  its client id and secret are set; the callback URL is
  `<DOCK_PUBLIC_URL>/api/auth/callback/<google|github>`.
- SSH listens on `DOCK_SSH_PORT` (default 2222); open it in your firewall.
  The host key is derived from `BETTER_AUTH_SECRET`, so it survives rebuilds;
  set `SSH_HOST_KEY` in `.env` to pin your own.
- Hosted ports work on a local install at `*.ports.localhost`. On a public
  install, run `./setup.sh --ports-domain ports.example.com` with a wildcard
  DNS record `*.ports.example.com` pointing at the server. Caddy issues each
  certificate on first use, only for exposed names. New ports are private: the
  edge asks the API before every request, and only members of the Dock's
  organization (through a sign-in redirect) or a Dock-bound API key get
  through. A port set to `public` is open to anyone with the URL. Port names are
  random (16 characters from a 32-letter alphabet, 80 bits) but each name gets
  its own certificate, which is public in Certificate Transparency logs. To keep
  names out of those logs, see [Wildcard certificate for ports](#wildcard-certificate-for-ports).
  Ports already exposed stay public. A Caddyfile from before private ports does
  not run the access check, so private ports answer `403` until you `git pull`
  and recreate the caddy service (`docker compose up -d caddy`).

Upgrade from `deploy/self-host/`: run `git pull` (compose and Caddyfile changes
ship with the release), then `./setup.sh --upgrade <version>`, for example
`./setup.sh --upgrade 0.2.0` (bare version, no `v`). It sets `DOCK_VERSION` in
`.env`, pulls the images, and restarts the stack; migrations run before the API
starts. By hand, edit `DOCK_VERSION` in `.env`, then run
`docker compose pull && docker compose up -d`. Back up the `pgdata` and
`minio-data` volumes and keep `.env`.

Upgrading to the release with Snapshot encryption, `docker compose up` stops with
`required variable MINIO_KMS_SECRET_KEY is missing a value` until `.env` has the
key. `./setup.sh --upgrade <version>` (or plain `./setup.sh`) adds it once. By hand,
append it yourself, then back up `.env`:

```bash
printf 'MINIO_KMS_SECRET_KEY=dock-snapshots:%s
' "$(openssl rand -base64 32)" >> .env
```

## Snapshot encryption

The bundled MinIO encrypts every snapshot object (SSE-S3). `minio-init` enables
default encryption on the bucket (`mc encrypt set sse-s3`), and MinIO's built-in
KMS wraps each object key with the static key in `MINIO_KMS_SECRET_KEY`
(`<key-name>:<base64 of 32 bytes>`). `setup.sh` writes that key to `.env` once and
never replaces it, on new installs and on upgrades of installs that lack one.

- **Back the key up with `.env`.** Losing it makes every stored snapshot
  unreadable; there is no recovery. Changing it has the same effect, so there is
  no in-place rotation. MinIO documents the static key as a minimal KMS (no key
  creation or rotation); for key management beyond that, use an external bucket
  with SSE-KMS.
- **Upgrading an existing install.** Objects written before the upgrade stay
  unencrypted; only new writes are encrypted. To re-encrypt, copy them into a
  fresh encrypted bucket and point the stack at it (stop writers first):

  ```bash
  docker compose stop backend
  docker compose run --rm --entrypoint /bin/sh minio-init -c '
    mc alias set dock http://minio:9000 "$SNAPSHOT_STORE_ACCESS_KEY" "$SNAPSHOT_STORE_SECRET_KEY" &&
    mc mb --ignore-existing dock/dock-snapshots-enc &&
    mc encrypt set sse-s3 dock/dock-snapshots-enc &&
    mc cp --recursive dock/dock-snapshots/ dock/dock-snapshots-enc/'
  # set SNAPSHOT_STORE_BUCKET=dock-snapshots-enc in .env, then:
  docker compose up -d
  ```

  Delete the old bucket (`mc rb --force dock/dock-snapshots`) once Snapshots
  restore from the new one. Or leave the old objects as they are and accept that
  they stay unencrypted.
- **External S3 or your own MinIO.** `MINIO_KMS_SECRET_KEY` does nothing there.
  Turn on default bucket encryption yourself (SSE-S3 or SSE-KMS); Dock sends no
  encryption headers, so it works with whatever the bucket enforces. On start the
  API checks the bucket and logs a warning when no default encryption is set; it
  never refuses to boot over it.
- **What it protects.** The key sits in `.env` on the same machine as the data, so
  SSE-S3 protects a stolen disk or a copied `minio-data` volume or backup, not a
  compromised host: anyone who can read `.env` or reach MinIO with its credentials
  reads every Snapshot. Object names, sizes and objects from before the upgrade are
  not encrypted. Store `minio-data` backups apart from `.env`.

## Verify images

Each release image (`dock-api`, `dock-api-migrate`, `dock-dashboard`) is signed
keyless with [cosign](https://docs.sigstore.dev/cosign/). Verify before you run it:

```bash
cosign verify ghcr.io/usedock/dock-api:<version>   --certificate-identity https://github.com/usedock/dock/.github/workflows/release.yml@refs/tags/v<version>   --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Use the same command for `dock-api-migrate` and `dock-dashboard`, with the
release number in place of `<version>`. Releases published by hand from the
Actions tab are signed with a branch identity instead of the tag one.

Installs created before the single baseline migration (October 2026) cannot
upgrade in place: the migration fails and the API never starts. Reset with
`docker compose down -v` (this deletes all Docks, Snapshots, and accounts), run
`./setup.sh` again, and re-enroll each host.

<Callout title="Keep SECRETS_ENCRYPTION_KEY and MINIO_KMS_SECRET_KEY">
  Losing `SECRETS_ENCRYPTION_KEY` makes stored provider keys and Environment
  secrets unreadable. Losing `MINIO_KMS_SECRET_KEY` makes every Snapshot
  unreadable.
</Callout>

## Add hosts

A host is a machine that runs Docks. It dials out to `DOCK_PUBLIC_URL` and needs
no inbound port. `./setup.sh --host` enrolls the control plane machine itself.
On any other Linux machine, from a checkout of `usedock/docklet` (`FLEET_TOKEN`
is in `.env`):

```bash
sudo bash scripts/bootstrap-host.sh \
  --fleet-url https://dock.example.com \
  --fleet-token "$FLEET_TOKEN" \
  --runtime microvm
```

The `--runtime` flag picks what the host provides:

- `microvm`: Firecracker on Linux KVM (bare metal or nested virtualization
  with `/dev/kvm`). The whole disk persists. The installer builds the image
  (several minutes, about 20 GB).
- `gvisor`: `runsc` on any Linux machine with Docker. Only `/home/user/work`
  persists across stop and resume.

The runtime is a property of the host, not of a Dock: a Dock gets the runtime of
the host it lands on. See [Runtimes and images](/concepts/runtimes). The
docklet repository covers hosts in depth.

## GitHub issue to pull request

Each instance registers its own GitHub App:

1. Put your email in `INSTANCE_ADMIN_EMAILS` in `.env` and run
   `docker compose up -d backend`.
2. In the dashboard open Developers > GitHub App > Register App and continue
   on GitHub.
3. Paste the App id, slug, private key, and webhook secret GitHub returns into
   `.env` (they are shown once and not stored by Dock), then run
   `docker compose up -d backend`.
4. Install the App on your repositories and link the installation to a
   workspace on Developers > GitHub App.
5. Add a model provider key under Developers > Provider keys.

Mention `@dock` in an issue comment to start a run.

## Connectors

Figma, Linear, Slack and Sentry work with pasted tokens out of the box. To offer
OAuth sign-in for a tool, create an OAuth app with it, register
`<DOCK_PUBLIC_URL>/v1/connectors/<kind>/oauth/callback` as the redirect URL and
set `<KIND>_CLIENT_ID` and `<KIND>_CLIENT_SECRET` (for example `LINEAR_CLIENT_ID`)
in `.env`. See [Connectors](/docs/connectors).

## Wildcard certificate for ports

By default Caddy issues one certificate per exposed port name on first use, and
every certificate is public in Certificate Transparency logs. With
`DOCK_PORTS_WILDCARD_TLS=1` Caddy instead obtains one `*.ports.example.com`
certificate through the ACME DNS challenge, so individual port names never get a
certificate of their own. Let's Encrypt issues wildcard certificates only
through the DNS challenge, and Caddy needs a DNS provider module for it, which
the stock `caddy:2` image does not include, so the shipped image is unchanged
and you switch to your own. Certificates already issued for earlier port names
stay in the logs.

1. Build a Caddy image with your provider's module from the
   [`caddy-dns`](https://github.com/caddy-dns) repositories. This follows the
   custom-build pattern on the official Caddy image page; `cloudflare` is only
   an example, so use your provider's module:

   ```dockerfile
   FROM caddy:2-builder AS builder
   RUN xcaddy build --with github.com/caddy-dns/cloudflare

   FROM caddy:2
   COPY --from=builder /usr/bin/caddy /usr/bin/caddy
   ```

   Build it with `docker build -t registry.example.com/dock-caddy:2 .` and push
   it. `./setup.sh --upgrade` and `docker compose pull` pull every image, so a
   local-only tag makes the pull fail.
2. In `.env`, set `DOCK_CADDY_IMAGE=registry.example.com/dock-caddy:2` and
   `DOCK_PORTS_WILDCARD_TLS=1`. `DOCK_PORTS_DOMAIN` and
   `DOCK_PORTS_SITE_ADDRESS` stay as `setup.sh --ports-domain` wrote them
   (`*.ports.example.com`).
3. Edit `deploy/self-host/ports-tls/1.caddy` for your provider. The `dns`
   subdirective takes the provider name and that module's own parameters:

   ```caddyfile
   tls {
   	dns cloudflare {env.CLOUDFLARE_API_TOKEN}
   }
   ```

   `propagation_delay`, `propagation_timeout` and `resolvers` can go in the same
   `tls` block.
4. Give the caddy service the credential, for example in
   `docker-compose.override.yml`, then restart it:

   ```yaml
   services:
     caddy:
       environment:
         CLOUDFLARE_API_TOKEN: your-token
   ```

   Run `docker compose up -d caddy`. The token needs permission to edit DNS
   records in the zone, and the wildcard DNS record must still point at the
   server.

With the flag set on the stock image, Caddy refuses to start (`module not
registered: dns.providers.cloudflare`, or your provider), which takes the whole
site down until you set the flag back to `0`. Wildcard mode hides which names
exist, not who can open them: keep new ports private.

## Network notes

- GitHub webhooks go to `<DOCK_PUBLIC_URL>/v1/github/webhooks`, so the API must
  be reachable from github.com.
- Docks used by GitHub runs reach the internet only through each host's egress
  proxy, which allows HTTPS to an allowlist that always includes the control
  plane. The control plane must therefore serve HTTPS on 443 with a publicly
  trusted certificate. If `DOCK_PUBLIC_URL` resolves to a private address, allow
  that range on each host with `--egress-allow-private 10.0.0.0/24`.
- Snapshot transfers go through the API's object proxy by default. Set
  `SNAPSHOT_STORE_PUBLIC_ENDPOINT` only if hosts can reach the object store
  directly.
- The stack uses `pgsty/minio` and `pgsty/mc` images; override with
  `MINIO_IMAGE` / `MINIO_CLIENT_IMAGE`, or point `SNAPSHOT_STORE_ENDPOINT` at any
  S3-compatible bucket.
